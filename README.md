# HLLSet в Cisco Packet Tracer

Сетевая модель HLLSet-системы в **Cisco Packet Tracer 9.0**: пользователи, маршрутизатор с ACL, сервер идентификации, планировщик, рой из 5 одинаковых «FPGA»-плат и общая решётка Grid.

На SBC-узлах PT работает настоящий HLLSet-код на Python. Ingest, CID (SHA-1 Roaring), materialize и HT-кардинальность совпадают бит в бит с Rust-крейтами `ewm-state-machine` (`hllset-core`, `hllset-morphisms`), см. [docs/RUST_PORT.md](docs/RUST_PORT.md).

Основа: чертёж архитектуры, репозиторий `hllset-next-v2` и статьи *Emerging World Models* и *The EWM Lattice and Its Worlds* (A. Mylnikov et al., 2026).

# тестирование модели HLLSet в Packet Tracer 9.0

Код: ветка с переносом на семантику `ewm-state-machine` (Rust), см. [RUST_PORT.md](RUST_PORT.md).

## 1. Как работает модель

```
user (PC) ──INGEST/QUERY──► DISPATCHER ──CHECK──► DATA          🟢 идентификация / 🟠 доступ
                                │
                                ├──PART (окна 0..k)──► FPGA1..5 ──MERGE──► GRID   🔴 модель / 🔵 решётка
                                └──SEAL / QUERY──────► любая FPGA ──SEAL/GET/PUT/REC──► GRID
```

**Загрузка текста (INGEST), как `hllset_morphisms::ingest` в Rust:**

1. DISPATCHER проверяет токен в DATA, имя документа и размер текста (не больше 400 слов).
2. Текст делится на слова, к нему добавляются метки: `[PAD] + слова + [PAD, PAD]`.
3. Позиции окон делятся на непрерывные куски, по одному на каждую готовую плату.
4. Каждая плата для своих окон считает:
   - 1-, 2-, 3-граммы с seed 0/1/2: каналы G1, G2, G3;
   - 4-граммы с seed 3: канал slide4, только для восстановления порядка;
   - `murmur3 → (reg, tz) → бит reg*32+tz`;
   - LUT: в бит окна записывается **первое** слово окна;
   - TF: сколько раз встретилось каждое слово.
5. Плата отправляет свою часть в GRID (`MERGE`). Часть хранится по номеру, поэтому повтор её не удваивает.
6. Когда пришли все части, `SEAL` объединяет их (OR), проверяет, что сумма TF равна числу слов, и регистрирует узел. CID = `h:` + SHA-1 сериализации Roaring проекции `G1 ∪ G2 ∪ G3`. Ключи G1/G2/G3 заносятся в hllsetLUT со счётчиком касаний TH.
7. Если имя уже было, старая версия сохраняется как `имя@N`, а в ответе выводится D/R/N между версиями.

**Запросы (QUERY)** выполняет любая свободная плата, по кругу:

| Операция | Что делает | Результат регистрируется как |
|---|---|---|
| `INFO`, `HIST` | CID и число бит; гистограмма `c_s` (кардинальность считает клиент) | — |
| `UNION`, `INTERSECT`, `DIFF`, `XOR` | OR, AND, AND-NOT, XOR битов | `A+B`, `A*B`, `A-B`, `A^B` |
| `DRN` | D = A\B, R = A∩B, N = B\A (A — прошлое состояние, B — текущее) | `D.A.B`, `R.A.B`, `N.A.B` |
| `LOOKUP` | для загрузки: восстановление текста **в исходном порядке** (проход по графу De Bruijn с учётом TF); для вычисленного узла: множество слов через LUT пользователя | — |
| `TOKENS` | множество слов загрузки без порядка | — |
| `LIST`, `STAT`, `HLUT` | имена пользователя, его статистика, его записи hllsetLUT | — |

## 2. Как читать ответы

```
INGEST doc1 -> OK | doc1 | tokens=9 | cid=h:7d9a… | bits=30 | G1,G2,G3=h:0762…,h:5fc7…,h:77df… | prev=… | boards=FPGA1:3 FPGA3:3 …
```

| Поле | Значение |
|---|---|
| `tokens` | число слов |
| `cid` | адрес узла в решётке (одинаковое содержимое → одинаковый CID) |
| `bits` | число единичных бит в проекции G1∪G2∪G3 (примерно 3 на слово) |
| `G1,G2,G3` | CID каналов (начало), записаны в hllsetLUT |
| `prev` | `-` — имя новое; иначе `имя@N <CID> D= R= N=` — разница с прошлой версией |
| `boards` | какие платы считали части и сколько окон каждая |

`card~30` в `HIST` — оценка кардинальности Хорвица–Томпсона, как в `hllset-core`. Она считается по проекции, поэтому для 9 слов получается около 30 (9 униграмм + биграммы + триграммы).

## 5.5 Ошибки старого кода, найденные анализом (до переноса)
1. Неполный документ регистрировался как готовый, если одна плата не ответила.
2. Повтор части после таймаута удваивал TF.
3. Узел не переподключался после разрыва.
4. Строка протокола без ограничения длины.
5. Табуляция склеивала слова, `|` обрезал текст.
6. Имена не проверялись.
7. Нет лимита размера текста.
8. `STAT` показывал глобальные счётчики: было видно, загружал ли кто-то такой же текст.
9. Токены бессрочные, перебор пароля не ограничен.

Всё исправлено. Подробности — в [RUST_PORT.md](RUST_PORT.md).

## 6. Где модель отвечает неверно (свойства алгоритма Rust, не ошибки порта)

### 6.1 Одинаковый CID у разных текстов без коллизии хеша
`ha ha ha` и `ha ha ha ha`, `a b a b` и `a b a b a b`.
- **Почему:** CID строится по **множеству** 1-, 2- и 3-грамм. Начиная с трёх повторов новых n-грамм не появляется, а TF в CID не входит.
- **Следствие:** узел решётки один, а тексты разные. Различить их можно только по записи загрузки (TF), но не по CID.

### 6.2 Коллизии хеша (`fact` / `note`)
- Бит = `reg*32 + tz`, где tz распределён геометрически: половина слов попадает в tz = 0. Поэтому вероятность совпадения бита у двух случайных слов ≈ 1/3072, а не 1/32768.
- По «парадоксу дней рождения» уже примерно при 46 разных словах совпадение в G1 вероятнее, чем нет. Среди 2 722 слов документации архива нашлось **589 групп** с общим битом G1: `chat/out`, `copy/earns`, `fact/note/seal` и др.
- **Следствие:** пересечения и `LOOKUP` вычисленных узлов могут содержать «чужие» слова. В Rust это задумано: «probabilistic restoration», сохраняются все кандидаты.
- **Сравнение со старой моделью** (только униграммы, один seed): там одна коллизия давала одинаковый CID у разных документов, например `core` и `next` при seed 101. В новой схеме совпасть должны ещё и 2-, 3-граммы, поэтому одной коллизии мало.

### 6.3 Неверный порядок при восстановлении
`нет да да нет да да да нет` → `нет да да да нет да да нет`.
- **Почему:** порядок восстанавливается проходом по графу n-грамм. При повторах у графа бывает несколько путей с одинаковым набором 2-, 3- и 4-грамм и одинаковыми TF. Жадный проход берёт первый подходящий.
- На случайных последовательностях из 2–4 слов с повторами ошибка порядка ≈ **2.8%** (83 из 3000, проверено на Rust). На обычных фразах без длинных повторов (`to be or not to be`, тексты user1) порядок восстанавливается верно.

### 6.4 Пересечение никогда не пустое
У каждого документа есть биты PAD и PAD·PAD, поэтому `A*B` всегда содержит минимум 2 бита. Для проверки «есть ли общие слова» надо смотреть `LOOKUP`, а не число бит.

## Быстрый старт

1. Собрать сеть по [docs/PLAN.md](docs/PLAN.md) и вставить конфиги из `configs/`.
2. Проверить связность и ACL по [docs/TESTS.md](docs/TESTS.md).
3. Вставить скрипты из `scripts/` в `main.py` на каждом SBC и запустить по порядку GRID → FPGA1–5 → DATA → DISPATCHER → user1 → user2 → user3.

Изменять нужно модули в `src/`, а не готовые скрипты. После правок:

```
python src/build.py scripts
pip install -r tests/requirements.txt
python tests/check_murmur.py src
python tests/sim.py scripts
python tests/verify.py scripts
```
