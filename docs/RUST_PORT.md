# Перенос на семантику ewm-state-machine (Rust) и результаты проверки

## Что теперь совпадает с Rust бит в бит

| Что | Rust (ewm-state-machine) | Где в PT-коде |
|---|---|---|
| Хеш и позиция | `murmur3_x64_128(bytes, seed).low64`, `bit = reg*32 + tz` | `src/hll16.py` |
| Ingest | `[PAD] + токены + [PAD, PAD]`; 1/2/3-граммы с seed 0/1/2 (G1/G2/G3); 4-граммы с seed 3 (slide4, без LUT); n-грамма = части через байт NUL | `src/morph.py` `ingest_part` |
| LUT | волокно бита хранит **первый** токен окна, только для реальных позиций 1..n | `ingest_part` |
| TF | счётчик вхождений реальных токенов | `ingest_part`, GRID `SEAL` |
| CID | `h:` + SHA-1 сериализации Roaring (cookie 12346; array ≤ 4096 бит, иначе bitmap 8 КБ) | `src/planes.py` `roaring_bytes`, `cid_of` |
| Ключ ingest | CID проекции `G1 ∪ G2 ∪ G3` (slide4 в проекцию не входит) | `morph.seal` |
| hllsetLUT | `(имя, ключ) → TH`: регистрация G1/G2/G3 + touch при каждом ingest | GRID `HLUT` |
| Materialize | LUT-first, все кандидаты; упорядоченный проход по De Bruijn с ограничением по TF, проверкой 2/3/4-грамм и бюджетом 20 000 | `morph.materialize_ordered` (итеративно, без глубокой рекурсии) |
| Кардинальность | `cardinality_ht` из hllset-core (экстраполяция насыщенных позиций, округление) | `src/card.py` (на хосте) |
| D/R/N | `D = H(t-1)\S(t)`, `R = H(t-1)∩S(t)`, `N = S(t)\H(t-1)` | FPGA `DRN`, GRID `SEAL` при повторном ingest |

Проверка: `python tests/check_rust.py src` сравнивает с эталонами, полученными из самих Rust-крейтов (`tests/rust_golden.json`). Дополнительно прогнано 600 случайных текстов (кириллица, эмодзи, CJK, повторы) и случайные разбиения между платами — 0 расхождений. CID и HT проверены на множествах от 0 до 32 768 бит.

## Что изменилось в модели

- **Один мир хеширования.** В Rust seed каналов зашиты: `[0, 1, 2]` и 3 для slide4. Seed пользователей (101/102/103) убран, иначе CID не совпали бы с Rust. Теперь один и тот же текст у разных пользователей даёт **один и тот же узел** (content addressing). Изоляция миров идёт через LUT: пользователь восстанавливает токены только через LUT своих загрузок. Этот момент стоит обсудить с автором теории: в статье мир описан как `w = (h, seed)`, а в Rust-коде его роль выполняют LUT и гейты.
- **Swarm делит работу по позициям окон**, а не по токенам round-robin: n-граммы требуют соседей. Части объединяются в GRID по job, `SEAL` регистрирует результат только когда пришли все части.
- **Именованные HLLSet неизменяемы.** Повторный ingest под тем же именем создаёт новую версию, старая остаётся как `имя@1`, в ответе есть D/R/N к прошлой версии.
- Новые запросы: `LOOKUP` (упорядоченное восстановление для загрузки, множество для вычисленного узла), `TOKENS` (no_order), `HLUT`.

## Найденные ошибки старого кода (исправлены)

1. Если одна из плат не отвечала, ingest всё равно отвечал OK и регистрировал **неполный** документ с неверным CID. Теперь часть повторяется на другой плате, иначе ingest отменяется.
2. Повтор после таймаута удваивал TF. Теперь части идемпотентны (хранятся по номеру).
3. После потери соединения `Peer` навсегда оставался «ready» и не переподключался.
4. Буфер строки не был ограничен: длинная строка без `\n` занимала память узла.
5. Табуляция и перевод строки склеивали слова (`a\tb` → `ab`).
6. `|` внутри текста молча обрезал текст.
7. Имена документов не проверялись: пустое имя, имена с `+ * - . /` пересекались с именами результатов (`doc1+doc2`). Теперь имя только `a-z 0-9 _`.
8. Нет лимита размера: большой текст надолго занимал платы. Теперь не больше 400 токенов.
9. `STAT` показывал глобальное число узлов. Из-за дедупликации по содержимому по нему было видно, загружал ли кто-то другой такой же текст. Теперь `STAT` показывает только данные пользователя.
10. Токены доступа без срока жизни и без ограничения попыток входа. Теперь TTL 30 мин, блокировка на 60 с после 5 неверных паролей.

## Где модель отвечает неверно (свойства Rust-алгоритма, не ошибки порта)

| Случай | Что происходит | Почему |
|---|---|---|
| `ha ha ha` и `ha ha ha ha` | **одинаковый CID** при разном тексте | при повторах множества 1/2/3-грамм совпадают; это совпадение без коллизии хеша |
| `a b a b` и `a b a b a b` | одинаковый CID | то же |
| `нет да да нет да да да нет` | восстанавливается как `нет да да да нет да да нет` | неоднозначность графа De Bruijn; на случайных текстах из 2–4 слов с повторами ≈ 2.8% ошибок порядка |
| `fact` и `note` (без общих слов) | `INTERSECT` = 3 бита, `LOOKUP fact*note` → `fact note` | коллизия G1: оба слова попадают в один бит (seed 0) |
| любые два документа | пересечение никогда не пустое (≥ 2 бита) | атомы PAD и PAD·PAD общие у всех документов |

**Коллизии хеша — частое явление.** Позиция `(reg, tz)` распределена неравномерно: половина вероятности приходится на tz = 0. Поэтому вероятность совпадения двух слов ≈ 1/3072. Среди 2 722 английских слов из документации репозитория нашлось 589 групп слов с общим битом G1 (например `chat/out`, `copy/earns`, `fact/note/seal`). Примерно с 46 разных слов совпадение в G1 становится вероятнее, чем нет.

В старой модели (только униграммы, один seed) такая коллизия сразу давала **одинаковый CID у разных документов**, например `core` и `next` при seed 101. В Rust-схеме различаются ещё 2-граммы и 3-граммы, поэтому одной коллизии для этого мало. Остаются только структурные совпадения из таблицы выше.

## Ограничения, которые остаются

- GRID доверяет платам, а платы доверяют полю `user` от диспетчера. Изоляция держится на ACL. Если скомпрометировать любую FPGA, будут доступны все миры.
- `random` в PT не криптостойкий; пароли хранятся открыто в DATA.
- Всё хранится в памяти SBC.
- Ветка ewm-git / ewm-app (коммиты `t:`, DAG, кольца) не перенесена: для PT это слишком тяжело. Перенесено ядро hllset-core + hllset-morphisms.
