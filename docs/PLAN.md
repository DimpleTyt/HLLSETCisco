# HLLSet в Cisco Packet Tracer 9.0 — план сети, этапы 1–2

## 1. Что поменяли статьи (EWM + companion note)

| Из статьи | Как это ложится на сеть |
|---|---|
| **Пользователь = мир** `w = (h, s)`: хеш-функция + seed (companion §3.1) | DATA server при входе выдаёт пользователю токен **и его seed**. FPGA хешируют токены этого пользователя его seed'ом |
| **Одна общая решётка**, много пишущих; union монотонен — «нельзя построить ничего неправильного» (§2.3, Principle 2.1) | **Grid** — одна общая решётка для всех. Платы роя пишут в неё без блокировок и синхронизации (OR) |
| **Изоляция миров — через LUT**, а не через биты (Principle 3.2) | **User's lookup table** = LUT мира пользователя внутри Grid. Grid отдаёт LUT только владельцу мира |
| Изоляция структурная, **не криптографическая** (Remark 3.10) | Поэтому нужны сетевые меры: VLAN, ACL, токены. Это обоснование сетевой части для документации |
| **Existence is registration**: HLLSet существует только после регистрации в hllsetLUT по SHA-1 (Principle 3.1) | Grid ведёт `sha1-hllsetLUT`. Каждая операция возвращает CID `h:<sha1>` |
| Регистрация идемпотентна → повторная отправка безопасна (Prop. 3.3) | Если FPGA не уверена, что Grid получил плоскость, — просто шлёт ещё раз |
| Swarm: «два узла, ингестящие одни токены, дают одинаковые HLLSet» (EWM §3.3) | Рой одинаковых плат, диспетчер раздаёт задачи любой свободной |

## 2. Топология

```
                         [R1  ISR4331]
                              | G0/0/0  (router-on-a-stick, DHCP, ACL)
                              | trunk
                         G0/1 |
 ADMIN ---Fa0/10--- [SW-CORE 2960] ---Fa0/1--- DATA (SBC)
                     |       |   \---Fa0/2--- DISPATCHER (SBC)
               Fa0/24|       |G0/2
               trunk |       | trunk
                G0/1 |       | G0/1
             [SW-USERS]    [SW-SWARM]
             Fa0/1..3        Fa0/1..5            Fa0/10
            PC1 PC2 PC3    FPGA1..FPGA5 (SBC)    GRID (SBC)
```

Кабели: PC/SBC ↔ коммутатор и R1 ↔ коммутатор — прямой (Copper Straight-Through); коммутатор ↔ коммутатор — перекрёстный (Copper Cross-Over). Можно просто использовать «молнию» (Automatically Choose Connection Type).

|---|---|---|---|

| 99 | MGMT | 192.168.99.0/24 | 192.168.99.1 |

| Узел | Модель PT | Порт | IP / маска / шлюз |
|---|---|---|---|
| PC1–PC3 | PC-PT | SW-USERS Fa0/1–3 | DHCP (выдаст .100 и выше) |
| ADMIN | Laptop-PT | SW-CORE Fa0/10 | 192.168.99.10 /24, gw .99.1 |
| DATA | SBC-PT | SW-CORE Fa0/1 | 192.168.20.10 /24, gw .20.1 |
| DISPATCHER | SBC-PT | SW-CORE Fa0/2 | 192.168.20.20 /24, gw .20.1 |
| FPGA1–5 | SBC-PT | SW-SWARM Fa0/1–5 | 192.168.30.11–15 /24, gw .30.1 |
| GRID | SBC-PT | SW-SWARM Fa0/10 | 192.168.40.10 /24, gw .40.1 |

На SBC сначала задаётся IP в Config → Ethernet0 (Static), и только **после этого** шлюз в Config → Settings (Interfaces: Ethernet0 → Static). Смена режима IP на интерфейсе сбрасывает шлюз.

## 4. Прикладные порты (понадобятся на этапе 3)

| Сервис | Узел | TCP-порт |
|---|---|---|
| API модели (вход, загрузка, запросы) | DISPATCHER | 5000 |
| Учётки, токены, seed'ы миров | DATA | 5001 (только внутри VLAN 20) |
| Плата роя | FPGA1–5 | 5100 |
| Решётка + hllsetLUT + LUT пользователей | GRID | 5200 |

Тестовые пользователи (на DATA): `user1/pass1`, `user2/pass2`, `user3/pass3`; seed'ы миров — **101, 102, 103** (не пересекаются с канальными seed'ами 0/1/2 из материализатора).

## 5. Политика доступа (этап 2, ACL на R1)

| Откуда → куда | Разрешено |
|---|---|
| USERS → | только DISPATCHER:5000 (+ ping DISPATCHER и шлюза) |
| DISPATCHER → | ответы пользователям, FPGA:5100 |
| SWARM → | ответы DISPATCHER, GRID:5200 |
| GRID → | только ответы FPGA |
| DATA → | никуда за пределы VLAN 20 (с DISPATCHER общается напрямую в своём VLAN) |
| MGMT (ADMIN) → | ping и SSH куда угодно |

ACL входящие (`in`) на подынтерфейсах; обратный TCP-трафик пропускается по `established`.

## 6. Порядок сборки

1. Расставить устройства и кабели по разделу 2.
2. Вставить `configs/R1.txt`, `configs/SW-CORE.txt`, `configs/SW-USERS.txt`, `configs/SW-SWARM.txt` (CLI → режим `Switch>`/`Router>`, вставка целиком).
3. Задать IP на SBC и ADMIN, на PC включить DHCP.
4. Проверить этап 1 по `docs/TESTS.md` — всё пингуется со всем.
5. Вставить `configs/R1_ACL.txt` и проверить этап 2 по той же таблице.

Если какая-то команда в PT 9.0 выдаст ошибку — пришли текст ошибки, поправлю.

## 7. Особенности Packet Tracer 9.0 (найдено при сборке)

- У SBC-PT нет Ethernet-порта по умолчанию — ставится модуль `PT-IOT-NM-1CFE` во вкладке Physical (при выключенном питании); порт появляется как `Ethernet0`.
- У SBC нет командной строки: ping с них — через Simple PDU; для ручных проверок нужен ADMIN (Laptop-PT).
- Шлюз на SBC задаётся отдельно для каждого интерфейса (Settings → Interfaces) и сбрасывается при смене режима IP на интерфейсе.
- После переключений Static ↔ DHCP SBC может перестать отвечать даже при верных настройках. Лечится перезапуском Packet Tracer и повторным вводом IP и шлюза (сначала IP, потом шлюз).
- R1 при выдаче DHCP проверяет адрес пингом и заносит занятые в `show ip dhcp conflict` — очищается `clear ip dhcp conflict *`.
- Пароли: enable `Cisco123!`, SSH `admin` / `Admin123!`. Вставляя конфиг в устройство, где уже задан enable secret, начинать со строки `configure terminal`.
- Python на SBC работает поверх JavaScript: целые точны только до 2^53, побитовые операции 32-битные — 64-битный хеш считается 16-битными «кусочками».
- Проект PT запускается с файла `main.py`; файл с другим именем не стартует.
- Обработчики TCP (`onReceive`, `onNewClient`, `onConnectionChange`) должны быть обычными функциями: методы класса PT не вызывает.
